- Mechanisms: Every mutation runs inside one transaction that locks the active account, then the `ai_runtime_sessions` row, then the ledger row, each `FOR UPDATE`. Locking the session row also serializes concurrent ledger opens, so no insert-conflict path is needed, and it is where a ChatGPT session is refused as `not_applicable` and a foreign session as `not_found`. The conservative maximum is computed only in `Decimal` and rounded with `:ceiling` at scale 4, so a one-token turn reserves `0.0001` rather than `0.0000` and the estimate can never under-reserve; unit prices are stored per one million tokens at `numeric(18,8)` and amounts at `numeric(12,4)`, matching the pinned ceiling. Outstanding reservations live in one `jsonb` map on the ledger row keyed by idempotency key, deliberately not a second table, because a reservation entity is not part of the approved data model. A replay with identical token bounds returns the stored reservation even if the registered price has since moved, while the same key with different bounds fails as `duplicate_reservation`, mirroring the `pin_session` idempotent-versus-conflict pattern. Over-allocation is defended three times: the row lock, an application invariant that `reserved_amount` always equals the decoded reservation sum, and a database `CHECK (reserved_amount >= 0 and observed_amount >= 0 and reserved_amount + observed_amount <= ceiling)`. Abandoned reservations are released, never charged, after a configurable 900-second default read through `Application.get_env/3` with no configuration-file entry. The price registry defaults to an empty map, so an unconfigured deployment refuses every reservation; each lookup revalidates the whole registry, and any malformed, negative, zero, unparseable, oversized, credential-shaped, or key-versus-version mismatched entry makes the registry untrustworthy as a whole and yields `missing_price`, while an expired newest registration yields `stale_price` and a currency mismatch against the ledger yields `missing_price`.
- Accepted implementation decisions: A pause writes only `paused`, `pause_reason`, and `paused_at`; `reserved_amount`, `observed_amount`, and `outstanding_reservations` are provably untouched and a later successful reservation clears the pause. This follows the approved entity, which lists pause state as ledger row content, while preserving the rule that a pause allocates no capacity and preserves the pinned configuration. Reconciliation takes the observed cost rather than observed tokens, because per-entry unit prices are not retained, and refuses an observed cost above its own reservation. Per-turn token bounds are required and must not exceed the ledger's approved bounded configuration, and re-opening a ledger with different bounds fails as `configuration_conflict`.

The behavior fails closed and is correct for the currently approved providers; the deployment's real price source is release-gated, so the decision is recorded rather than resolved here.
