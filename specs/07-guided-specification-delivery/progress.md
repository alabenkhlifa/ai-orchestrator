### 2026-08-01 - Task 36 complete: the fewest people who have to act are told

- Completed: Added `Delivery.RunNotifications` and hooked it to every site that commits one of the three run events. A paused, review-ready, or terminally failed run now reaches exactly the people AC-27 names, once each, through the shared account-level store (AC-27, entity:Notification).
- **No migration and no new schema.** `account_notifications` already reserved the `delivery.` event-type namespace, and its conflict target `[:account_id, :event_type, :subject_ref, :event_version]` already *is* the required "unique event-type, run-state-version and recipient key". The key is `{recipient, "delivery.run_*", run.id, run.state_version}` — inventing a dedup concept beside it would have been a second answer to a question the store already answers.
- **Projection runs after the authoritative transition commits, never inside it**, for two independent reasons. `DeliveryStore.commit/3` accepts only the fixed vocabulary in `operations/0`, which has no notification operation; and `account_notifications` is a hosted record while delivery state may be device-authoritative, so the two cannot share one transaction. What that costs is at-least-once delivery, and the idempotent key is what makes it safe — which is exactly the durable-projection decision `design.md` already records. It also sidesteps the recurring one-write-per-record trap, because the projector never adds a step to a delivery commit.
- The version half of the key is the run's state version **after** its transition, so a run that blocks a second time is a new notification rather than one the key swallows. **One asymmetry, deliberate and commented in place:** review handoff moves only the feature — `RunTransitions.apply/2` never touches the run — so the run's version is not bumped there. Blocked and failed take the post-commit run out of the commit result; ready-for-review reads it back through `DeliveryStore.fetch_run/3` rather than trusting a caller's snapshot that may predate the attempt the run is now on.
- Five committing sites, two of which the task plan does not obviously name. `blocking.ex` and `retry.ex`'s `fail_terminally/1` are the expected two, and the failed notification is emitted only after the terminal state is recorded, as the business rule requires. Beyond those: `reconciliation.ex`'s terminal path commits the identical terminal shape for an execution nobody can recover and never flows through `retry.ex`; and the contradictory-feedback block lives in **`review.ex`, not `review_continuation.ex`** — the continuation only returns a plan and commits nothing, so hooking it would have notified nobody. `review_continuation.ex` is unmodified.
- Which rejection blocked the run is read from `continuation.payload["blocked_for_specification"]`, the same flag `Review.blocked_for_specification?/3` reads. Task 35 established that this judgement gets one derivation; a projector that re-inferred it from the feature's `Blocked` status would have been the second.
- Cancellation is deliberately not notified. `canceled` is a different terminal state from `failed` and AC-27 does not name it; a scheduled automatic retry is likewise silent, because recovery still in progress asks nobody to act. Both are pinned by tests rather than left as omissions.
- **No storage-mode branch anywhere.** The projector asks participation for recipients and writes nothing when none resolve. Because `Participation.owner/1` refuses any non-hosted project, a genuinely device-authoritative project resolves nobody — which is what keeps its feature titles out of the hosted database. The privacy property falls out of fail-closed recipient resolution instead of a special case, and the module says so where a later reader would otherwise add one. Tasks 41 and 48 own proving it.
- A projection that cannot store anything never turns a committed lifecycle transition into a refusal; it logs and the caller proceeds. The log carries the event type, run id, step, and the changeset's *error field names* — never their values, because an `inspect` of the changeset would put the feature title in the log.
- Recipient resolution consumes rather than re-derives: `Assignment.responsible/2` already resolves assignee, then creator, then owner, and already refuses anyone who is no longer a member. Only the initiator is checked against current membership here, because it is a historical account reference on the run. A run nobody started and an initiator who has left both resolve to nobody. Bodies are bounded on a grapheme boundary before they are built, so the longest title a feature may hold can never be the reason a notification fails to store.
