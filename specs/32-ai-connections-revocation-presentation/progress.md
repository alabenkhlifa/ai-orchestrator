# AI Connections Revocation Presentation Progress Log

### 2026-08-05 - Product decisions resolved; specification approved

- Decisions resolved, all accepted as recommended and moved into the business rules and acceptance criteria: each suppressed panel collapses to the wording the screen already carries rather than disappearing, so shipped-but-unreachable copy becomes reachable and the panel list keeps agreeing with the connections list; a revoked connection stays listed until its existing deletion schedule removes it and the screen states that removal is scheduled, because the record still exists and a rights export would still return it; a revocation left pending by an unreachable worker states that new AI work is already denied and that worker-local credential removal remains outstanding, naming no retry count or adapter error; each entry offers one plain sentence pointing at linking a replacement and no control that re-enables a revoked connection; and the correction covers all four states in which the screen already refuses a refresh.
- Scope widened deliberately, from two states to four: `unavailable` and `incompatible` disable the same refresh controls and leave the same populated panels with the same unreachable wording, so limiting the fix to `revoking` and `revoked` would have left the identical defect in two states. AC-01, AC-02, and AC-04 were widened rather than duplicated, and no task was added, so the slice-size and task-size contracts are unchanged.
- AC-07 added for the indefinitely pending revocation, owned by Task 2. This case was not in the original finding: `deletion_scheduled_at` is set only at acknowledgement, so an unreachable worker leaves a connection listed indefinitely reporting only "Revocation pending", which reads as a transient delay while the owner's real question is whether the credential is gone.
- Technical decision settled rather than asked: `ModelCatalogs.current_catalog/3` and `Quotas.current_quota/3` keep their contracts and the fix stays presentation only, because adding a read-side eligibility check to `current_quota/3` would silently drop a run pinned to a just-revoked connection from real account-wide quota facts to `unknown` inside `RuntimeProjections.owner_projection/3` — approved AC-13 behavior in a `Verified` slice, which this specification has no authority to change.
- Task plan split from two tasks to three, forced by the Task Size Gate rather than by preference: adding AC-07 gave Task 2 four acceptance criteria, and the validator refused it. A size exception was not available, because an exception requires that splitting would create a concrete invalid intermediate state, which is not true here. Task 2 now owns what the owner reads about a connection's state and remaining options (AC-04, AC-07), and a new Task 3, depending on Tasks 1 and 2, owns the revoked reference's scheduled-removal statement and the cross-cutting proof that every statement this slice adds carries no forbidden value and stays usable on both layouts (AC-05, AC-06). Task 3 is last because its forbidden-value sweep can only cover copy that already exists. The slice stays `Slice size: Standard` at three tasks with a critical path of three.
- Status: requirements moved from `Draft` to `Approved` and the task plan from `Blocked` to `Not Started`. Task 1 is executable.
