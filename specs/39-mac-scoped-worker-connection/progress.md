# Mac-Scoped Worker Connection Progress Log

### 2026-08-28 - Task 1 complete: a configuration is valid with no project

- `workspace_root` had to become optional alongside `project_id`. `design.md`'s Proposed Approach names only the project, but its `The repository folder is not asked for here` decision already states that a worker connected this way has no repository. Leaving `workspace_root` enforced would have left a menu-bar-paired worker with nothing to store, which is the whole defect. This implements the recorded decision rather than changing it.
- Resolved mechanism: an absent project or repository folder is stored as an absent key, not a `null`, and `Worker.Supervisor` deletes the workspace-root application key instead of setting it to `nil`. The second matters beyond tidiness: a root left behind by an earlier configuration would otherwise point a projectless worker's runs at a folder it was never given.
- Discovery worth recording: `Configuration.load/1` has never refused an unrecognized `agent_adapter` string. It refuses only a blank one, and `Worker.Supervisor` deliberately falls back to `AgentAdapter.Unavailable` for anything unknown, which an existing test asserts. `mix worker.pair` is where an unknown adapter is actually refused. No new validation was added, because adding it here would have contradicted that established behavior.

### 2026-08-28 - Specification created from a real install that could never connect

- Found by the user working on an on-device project: the page showed `Unavailable` and said the worker was not running, while they believed the worker was connected.
- Diagnosis, by reading the running system rather than the specifications. `Configuration.load()` on the installed worker answered `{:error, :not_paired}`, so `GatewayConnection` had never started and `Worker.ConnectionStatus.status/0` answered `%{status: :unknown, updated_at: nil}`. In the development database every real worker row (`app_version 0.1.0`) carried `last_seen_at = NULL`; only `0.0.0-stub` rows carried a value, because the LiveView stand-in calls `Pairing.mark_seen/1` directly. `WorkerDiscovery.reachable?/2` answers `false` for a `nil` timestamp, so every real worker was unavailable by construction.
- Root cause: `Delivery.WorkerRegistry` is keyed by project and only a successful join on the project-scoped `worker:` topic reaches it, `WorkerLivenessRefresher` enumerates exactly that registry, and a worker paired from the menu bar has no project. `specs/38-worker-initiated-pairing/` recorded this outcome in its own Risks and deferred boundary. The dashboard was correct; nothing was regressed.
- Second defect found in the same pass, latent rather than active: `ConnectionStatus.set_connected/0` is called from `GatewayConnection.handle_connect/1`, which fires on socket connect before the join, and `handle_topic_close/3` never calls `set_disconnected/1` on a join refusal. Once a worker is configured, the menu bar can therefore say Connected while the control plane has attached nothing. Owned here by `AC-07` and `AC-08`.
- Product decisions taken with the user, all three as recommended: connection is scoped to the Mac with projects attaching afterwards rather than pairing once per project; the coding agent is chosen once per Mac; and the app reports Connected only once the control plane agrees.
- Scope: classified `focused specification`. One outcome, one workflow, one verification gate, eight tasks, longest `Depends on:` path of four.
- Deferred and named rather than implied: `LocalOnboardingLive`'s production `select_folder` answers `Connect the worker to open the folder picker` and only the development stand-in completes selection, so the accountless path still cannot choose a repository against a real worker. This slice makes the worker reachable, which that follow-on needs, and does not close it.
- No code changed in this update.
