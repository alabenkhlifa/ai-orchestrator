### 2026-09-03 - Specification created for the binding half of a live assessment

- Cause confirmed in code before anything was designed. `RepositoryMetadataAdapter.configured/0` falls back to `Unavailable`, no configuration file in any environment sets `:repository_metadata_adapter`, and the only setter is the `/_e2e` bootstrap controller, which is compiled out of normal builds. `specs/46-assessing-a-repository-on-a-mac/` recorded the same finding and classified it as `specs/14-repository-execution-profile/`'s release gate.
- Two further facts were found while scoping and they changed the plan. First, the worker-local computation already exists and is verified: `RepositoryAssessments.WorkerRepositoryMetadata.inspect/4` resolves the repository top level, proves root containment through links, and reads `HEAD`, returning exactly the four fields the contract allows. Nothing needs to be added to it. Second, nothing on either side knows where the repository is. `specs/40-worker-repository-selection/` deletes the chosen path on read by design, `HostedLocalRepositoryBinding` stores the project, the worker, and a validation time, and the project stores a portable identity, not a location.
- A third fact set the slice boundary. `finish_assessment/6` has no live caller either, and no command carries a scan. So a live adapter alone lets an assessment start and never complete. The user chose to deliver the binding half now and the live scan as a named follow-on, because the scan depends on the binding and the two are independently valuable.
- Product decisions taken with the user. The person points at the repository folder when a binding is prepared, reusing the panel the installed Mac app already serves, so no path is ever stored and the app needs no rebuild. The live proof covers both the hosted route and the device route, which is what `specs/14`'s gate means by each deployment profile.
- Engineering decisions recorded in `design.md`. The question rides the Mac-scoped attachment as `specs/40`'s selection does, the adapter stays synchronous and the screen moves the call into a monitored task so it can render a wait and a stop, the worker holds the answered folder in memory for the binding's 120 second life so the revalidation opens no second panel, `Worker.RepositorySelection` stays the Mac's one panel owner, and the live adapter is configured in `config/config.exs` with the test environment pinned to `Unavailable` so no existing suite changes behaviour.
- Privacy boundary is unchanged and stated as a rule and an acceptance criterion. The question and the answer carry only what `specs/14` already defined, refusals are single atoms so no Git message can travel, and the folder exists only in the answer file for at most one poll interval and in the release's memory for at most the binding's life.
- One widening is recorded rather than hidden. `specs/40` kept the path inside one function; this slice keeps it in memory for up to two minutes. That is why the release-restart case is AC-08 and not an implementation detail.
- Scope: classified `focused specification`. One outcome, one workflow, one verification gate, eight tasks, longest `Depends on:` path of seven, no size exception. All three required capabilities are already provided by verified slices, so no task starts blocked.
- Consequence for neighbours, with nothing reopened. `specs/14`'s live-worker gate closes only when this slice and the deferred scan are both verified, and `specs/41-feature-delivery-from-the-ui/` and `specs/46` stay release-blocked until then.
