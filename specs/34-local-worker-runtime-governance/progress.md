### 2026-08-08 - Design corrected before implementation: no `ObservationAdapter.LocalWorker`, no ingestion

- Completed: `implement-spec` preflight for Task 3 read `lib/sdd_orchestrator/ai_runtime/observation_adapter.ex` in full before writing any code and found `ObservationAdapter.validate_provenance/3` — the gate `RuntimeObservations.ingest/3` runs unconditionally on every call — has exactly one accepting clause: `provider: "openai_codex"`, `source: "official_client"`, with a Codex-CLI-specific `source_version` pattern. Everything else is refused. A local-worker-sourced result, for either agent, can never honestly satisfy that provenance, so the originally planned `ObservationAdapter.LocalWorker` (this entry's predecessor below still describes it) was a dead end confirmed before any code existed for it, not a runtime failure discovered later. Zero implementation commits existed on `slice/34-local-worker-runtime-governance` at the time of this finding.
- Fix verified against the actual code, not assumed: `RuntimeProjections.owner_projection/3` and `participant_projection/4` (`lib/sdd_orchestrator/ai_runtime/runtime_projections.ex`) already handle an empty observation list as an ordinary case — `list_observations/3` returns `{:ok, []}`, `latest_observation/2` returns nothing, availability degrades to `:unknown` — so the pinned connection's model, effort, and quota still project correctly with zero ingested observations. The mechanism this slice now uses: a live, read-only elapsed-time-and-status snapshot computed directly from the referenced `AgentRun`/`RunAttempt`'s own already-existing state (no new module under `ai_runtime/`, no schema, no persisted observation), combined with the unchanged reused projection for connection/model/effort/quota. `capability:ai-runtime-observation` is still required and still consumed — through its projection functions only, never through `ingest/3`.
- Spec updates: `requirements.md` (Outcome, In Scope, Primary Workflow steps 6–7, two Business Rules, AC-05/AC-06/AC-07/AC-08 reworded from "ingested observation" to "computed"/"live runtime snapshot" — same substance, corrected mechanism), `design.md` (Context, Proposed Approach, Components Affected, Data and Access Boundaries, Interfaces, the observation-adapter Decision entry replaced with "A live computed snapshot instead of a persisted, ingested observation", one Risk bullet), `tasks.md` (Task 3 redefined from "Implement the lifecycle-derived local-worker observation adapter" to "Compute a governed run's live runtime snapshot"; Task 4 redefined from "Ingest one ordered observation at each governed run's lifecycle transition" to "Assemble the combined projection for a governed run"; Task Size Gate and Slice Size Gate prose updated to match). Task count (seven), critical path (five), and every `Owns:`/AC/entity mapping are unchanged — this was a mechanism correction, not a scope or task-count change. `validate_spec.py` passed after the edit.
- Business rules, acceptance substance, and both accepted product forks from the entry below (observation-only enforcement, optional per-run connection) are unaffected: elapsed time and status still come only from the worker's own lifecycle, tokens and cost are still always unknown, and quota is still informational-only.

### 2026-08-08 - Specification created to bridge specs/33 and specs/11

- Completed: Created the child specification that closes the gap `specs/33-local-worker-run-execution` named in its own Out of Scope section and its tasks.md deferred list ("a run funded by a personal AI connection, a pinned model and effort, an enforced spending ceiling, and ingested runtime observations"), and that `specs/11-ai-runtime-governance`'s design document flagged as needing "an approved `update-spec` [that] defines manifest references, pause, resume, stop, cancellation, and continuation mapping" before a Slice 07-family consumer could use `capability:ai-runtime-session` and `capability:ai-runtime-observation`. Eight acceptance criteria are owned by seven tasks with a five-task critical path. One new owned entity, `LocalWorkerRunGovernance`, references both providers' identities without redefining either.
- Decisions resolved by the accountable user on 2026-08-08, both accepted as recommended: (1) enforcement depth stays observation-only — the worker's existing agent launch and credential resolution are unchanged, and spending-ceiling or quota-exhaustion pausing is not enforced against a local-worker run in this slice; (2) linking a personal AI connection stays optional per run rather than mandatory, so a run with no eligible connection keeps working exactly as the already-verified `specs/33-local-worker-run-execution` baseline, and Claude Code local-worker runs are not blocked by the absence of a Claude Code usage or quota adapter in `specs/11-ai-runtime-governance`.
- Scope classification: focused specification. One primary outcome (attribution, session pinning, lifecycle-derived observation, and presentation for a local-worker run), one coherent workflow from start-development through terminal state, and one verification gate proving both a governed and an ungoverned run end to end.
- Capability graph: consumer only. `capability:local-worker-run-execution` (provider `specs/33-local-worker-run-execution#Task 12`), `capability:ai-runtime-session` (provider `specs/11-ai-runtime-governance#Task 11`), and `capability:ai-runtime-observation` (provider `specs/11-ai-runtime-governance#Task 5`) are all `ready`; no provider file was edited. - Architecture finding that shaped the design: `RuntimeObservations.ingest/3`'s default `RPC` adapter queries the live Codex App Server process, which has no relationship to the CLI subprocess a local worker actually launches. Reusing it here would report facts about the wrong process, so this slice adds `ObservationAdapter.LocalWorker`, a second implementation of the same behaviour, sourced from the worker's own attempt lifecycle instead, with tokens and cost always reported unknown rather than guessed.
