# Assessing A Repository On A Mac Progress Log

### 2026-09-03 - Specification created after a delivered project could not reach a run

- Found by driving `specs/41-feature-delivery-from-the-ui/`'s release proof in a real browser, on a hosted project created by clicking through `specs/44-hosted-local-repository-projects/` and reached through `specs/45-hosted-session-project-access/`.
- Four of the five start preconditions were met by clicking: `ready`, `boundary`, `worker`, and `ai_connection`. The fifth reported `This project has no approved execution profile. Assess the repository, then approve one.`, the profile screen answered `No completed assessment with a verifiable minimized proposal envelope is available for this repository, so there is nothing to approve.`, and the assessment screen redirected away with no explanation.
- Root cause confirmed in code rather than inferred, and it sits in two places. `RepositoryAssessmentLive`'s `active_hosted_project?/1` and `RepositoryAssessments.authorize_project/2` both require `match?(%{state: "connected"}, project.repository_connection)`. A hosted project whose repository is on a Mac has no such row at all, because that row is GitHub-shaped and its repository id is a provider-issued integer such a repository never has.
- It is not a session problem and not caused by the two slices just merged. The same screen refuses a GitHub-signed-in owner of such a project in exactly the same way.
- The machinery already exists. The same screen's `:device` route assesses a Git repository on the machine in front of the person and works, so what is missing is only that the hosted route will not admit this project shape.
- Product decisions taken with the user: the screen names such a repository by reusing the device route's existing wording rather than adding a second phrasing for one fact, and an unreachable Mac is a state the screen shows with no start offered rather than a redirect. The redirect is what made this defect expensive to find.
- Engineering decisions recorded in `design.md`: assessability is redefined as reachability, satisfied by a connected GitHub connection or by a worker binding, and the two gates are changed as one so the screen and the domain cannot disagree about who may assess.
- Scope: classified `focused specification`. One outcome, one workflow, one verification gate, three tasks, longest `Depends on:` path of three. `Task 1` records a size exception because the two gates are one authorization rule.
- Consequence: `specs/41-feature-delivery-from-the-ui/`'s release gate stays open on this. Its remaining click path is add a feature, press `Start development`, and see the worker acknowledge, and the feature and its other four preconditions are already reachable.
- No code changed in this update.

### 2026-09-03 - Task 1 complete: one assessability rule, read by every gate

- The rule was in five places across four modules, not the two the specification predicted. Each refused the project one step further along: the screen's gate, `authorize_project/2`, `AssessmentStore.Hosted.put/2`, that store's `lock_project_binding/1`, and `ProfileStore.Hosted`'s `active_binding?/2` with its own `lock_project_binding/1`. Fixing a subset moved the refusal later rather than removing it, which is the defect itself, so `design.md` and this task's owned surfaces were corrected mid-task and the size exception rewritten.
- Two of the five refused by answering `nil`. The `lock_project_binding/1` functions read a `RepositoryConnection` and returned nothing without one, so a project on a Mac looked missing rather than refused. That is why the screen redirected with no reason.
- `RepositoryAssessments.assessable_hosted_project?/1` is now the one rule: hosted, active, and reachable through a connected GitHub connection or through a worker binding. The domain module owns it and the screen and both stores read down into it, so no caller can be more permissive than the authority.
- Authorization did not widen. `Participation.owned_project/2` still runs first at every gate, and the two identity checks beside `active_binding?/2`'s connection test, on `repository_provider` and `canonical_repository_id`, were kept. Only the question of whether the repository is reachable changed.
- The locking is unchanged in kind. `lock_project_binding/1` still takes `FOR UPDATE` on the project and now also on the binding row where one exists, and sets both associations on the struct so the predicate reads the locked rows rather than re-reading unlocked ones. A project with neither link still resolves to `nil`, so the GitHub path is byte-identical.
- Binding existence and worker reachability were never conflated in this code and still are not. No gate reads worker availability; that stays with `HostedLocalRepositoryBindings.connection_state/3` and is `Task 2`'s to render.
- A sweep of `lib/` for `lock_project_binding`, `RepositoryConnection`, and `state: "connected"` found no further copy inside the assessment or profile paths. Two matches elsewhere ask a genuinely different question and were reported rather than touched: `project_assistant/repository_source_authorization.ex` picking a GitHub access path, and `portability/github_reconnection.ex`, which is GitHub reconnection by definition.
- The refusal paths are proven, not just the success path. With the binding deleted, the profile append refuses `:stale_assessment` and writes nothing, the assessment put refuses `:unauthorized`, and the transition refuses while the pending row survives. An assessment naming another provider or another repository id is still refused, so neither retained identity check was lost.

### 2026-09-03 - Task 2 complete: the screen names the repository, and already named the unreachable Mac

- `hosted_repository_display/1` used to read the connection alone and fall through to the literal `Connected repository`, which for a repository on a Mac was both uninformative and misleading. It now matches on the pair of links and renders the local wording for the shape the assessment service admits: no connection, one worker binding. A connection that names itself is returned exactly as before.
- The wording is one owned value, `local_repository_display/1`, rendered by both routes. The device route's inline copy of the same sentence was replaced by a call to it, so the two routes cannot describe the same repository two ways.
- The label keys on the links, not on `repository_provider` or the storage mode, so this screen and the gates cannot disagree about which projects are which.
- The unreachable Mac needed no new code, and adding any would have been wrong. Once `Task 1` lets the screen open, an unreachable Mac leaves no reachable worker, so the screen already renders its owned `No worker is available right now. Start or reconnect one, then try again.`, disables the confirmation, never reaches the binding stage, and so never offers a start. A second sentence would have duplicated a fact the screen already states. Only proof was added.
- The state is proven to change nothing: no adapter event, no assessment row, and the project and binding rows compare equal to their pre-render structs.
- A correction to the task brief, found by trying it. An unattached worker cannot be used to reach the not-reachable state, because `Projects.register_project/3` writes the binding through `put_validated_binding/6`, which rolls the whole registration back for an unavailable worker. The test registers against an attached worker and then ages its `last_seen_at` past the staleness window, which is the real path anyway: the Mac sleeps or shuts down after it was bound.
- The label test was checked for vacuity by reverting the implementation, seeing it fail on `Connected repository`, and restoring it.
- Residual gap recorded, outside this task and not fixable by another message: when the bound Mac is unreachable but a different paired worker is, the screen still offers that other worker. The domain fails it safely at `prepare` with `:repository_mismatch` and writes nothing, but the refusal reads `That worker did not verify this project's connected repository`, which is GitHub-shaped for a repository on a Mac.
- Proof receipt: `Task 2` — scope `Focused` — command `mix test test/sdd_orchestrator_web/live/repository_assessment_live_test.exs` — exit `0`.
- 12 tests passed in that file. Regression run outside the focused proof: the assessment suites with the execution profile screen, 119 passed.
